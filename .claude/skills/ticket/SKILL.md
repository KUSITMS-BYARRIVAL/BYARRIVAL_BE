# /ticket

인자: `$ARGUMENTS` (예: `DCK-22` 또는 `DCK-22 #12`)

## 1. 범위 확인

1. `.claude/spec/roadmap.md`에서 티켓을 찾아 작업명, 스프린트, 관련 기능 ID, 의존 관계를 확인한다. 표에 없으면 사용자에게 묻고 멈춘다.
2. 관련 기능 ID가 있는 `.claude/spec/features/<그룹>.md`만 읽는다.
3. 의존하는 티켓의 코드가 아직 없으면 알리고, 그대로 진행할지 묻는다.
4. 관련 기능의 "확정 필요", "제안", "협의" 항목과 roadmap의 미확정 목록 중 이 티켓에 걸리는 것을 뽑는다.

## 2. 구현 계획 공유

다음을 짧게 정리해 사용자에게 보여 주고 확인을 받는다.

- 만들 API 목록: Method, URI, Request, Response
- 만들거나 바꿀 Entity와 테이블
- 도메인 ErrorCode 목록 (명세의 예외 처리 칸 기준)
- 미확정 항목과 내가 쓸 가정값

미확정 항목은 사용자가 답하기 전까지 임의로 정하지 않는다.

## 3. 이슈와 브랜치

1. 인자에 이슈 번호가 있으면 그 이슈를 쓴다. 없으면 `.claude/conventions/workflow.md` 형식으로 이슈 초안을 보여 주고, **사용자가 승인한 뒤에만** `gh issue create`로 만든다.
2. `dev`를 최신으로 맞춘 뒤 `<타입>/#<이슈번호>-<설명>` 브랜치를 만든다. 사용자가 이미 만든 브랜치에 있으면 그대로 쓴다.

## 4. 구현

- `.claude/conventions/backend.md`를 따른다.
- 순서: Entity·Repository → ErrorCode → DTO → Service → Controller
- 명세의 처리 로직을 번호 단위로 옮기고, 해당 로직이 있는 메서드에는 기능 ID를 주석으로 남기지 않는다(이력은 커밋과 PR에 남긴다).
- 시각과 랜덤이 들어가는 로직은 `Clock`, `Random`을 주입받는다.

## 5. 테스트

- 명세의 처리 로직마다 성공 케이스를, 예외 처리 칸마다 실패 케이스를 작성한다.
- `./gradlew test`를 실행하고 결과를 그대로 보고한다. 실패하면 고친 뒤 다시 실행한다.

## 6. 마무리

- 구현한 기능 ID, 테스트 결과, 남은 미확정 항목을 정리한다.
- 커밋은 하지 않는다. 사용자에게 `/ship`으로 이어갈지 묻는다.
